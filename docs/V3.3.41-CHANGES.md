|---|------|------|

### 1.1 根因

CI 日志 `wine-build-log-arm64ec (8).zip` 的最终阵亡点：

```
dlls/winegstreamer/unixlib.c:285:2: error: Bad arch
dlls/winegstreamer/unixlib.c:288:25: error: use of undeclared identifier 'arch'
make: *** [Makefile:205664: dlls/winegstreamer/unixlib.o] Error 1
```

`dlls/winegstreamer/unixlib.c` 带 `#pragma makedep unix` → 属 **unix 侧**库对象，
由 **host 编译器**编译。arm64ec 形态的 unix 侧是 aarch64
（`aarch64-linux-android28-clang`），而该文件的 GStreamer registry 架构判定
只有 x86 两支：

```c
#if defined(__x86_64__)
        const char *arch = "/registry.x86_64.bin";
#elif defined(__i386__)
        const char *arch = "/registry.i386.bin";
#else
#error Bad arch            // ← aarch64 落这里
#endif
```

aarch64 既非 `__x86_64__` 也非 `__i386__` → 直落 `#error`；`#else` 分支里
`arch` 变量根本没有声明 → 连带 `undeclared identifier 'arch'`（第 288 行
`strcat(gst_reg, arch)`）。

- x86_64 形态无事：unix 侧 = x86_64 → 首分支命中；
- proton_10.0+ 无事：Valve 已把 aarch64 分支补上。

全树扫描确认：**`Bad arch` 在整个 wine 树仅此一处** —— 这是 proton_9.0
arm64ec 构建的**唯一**剩余阻塞点（构建日志中 `error:` 仅此 2 条，其余皆 warning）。

### 1.2 修法（逐字回移 Valve 上游）

**新增** `bionic-rootfs/projects/hangover-wine/0022-fix-winegstreamer-unixlib-arch-proton.patch.proton`：

```c
 #elif defined(__i386__)
         const char *arch = "/registry.i386.bin";
+#elif defined(__aarch64__)
+        const char *arch = "/registry.aarch64.bin";
 #else
 #error Bad arch
 #endif
```

与 Valve `proton_10.0` 分支同款（`/registry.aarch64.bin` —— 该文件名由
**unix 侧** gstreamer 自身 arch 决定，与 PE 侧目标架构无关）。

**配方接入**（`projects/hangover-wine/build.sh`，新增 (g) 段）：
- 门控：`unixlib.c` 含 `#error Bad arch` 且不含 `defined(__aarch64__)` 时才
  套用；proton_10.0+/hangover/official 树自动跳过；
- `--fuzz=0` 逐字锚点，失败仅告警不中断；
- **硬校验**：arm64ec 形态下若仍缺 aarch64 分支 → `::error::` + `return 1`
  （防锚点漂移静默落空）。

### 1.3 验证

- 补丁在真实 proton_9.0 源码树上 `patch -p1 --fuzz=0` **干净应用**，
  反向应用亦干净（恰好命中一次，无重复定义）；
- 应用后文件与 proton_10.0 对应片段**逐字一致**；
- `bash -n build.sh` 语法通过。

## 2. 性能优化（用户问题 1）

### 2.1 mesa / rootfs 的 zink → libEGL（用户明确点名「rootfs 缺失的 zink 构建 libegl」）

**问题**：`bionic-rootfs/projects/mesa/build.sh` 里 `-Dgallium-drivers=softpipe,freedreno,zink`
只是**请求** zink。meson 侧 zink 有多条前置条件（Vulkan loader 必须在链、
`freedreno-kmds=msm,kgsl` 决定 `with_dri_platform=pseudo-drm`、
GLX=dri 形态还要求 libxcb 的 `xcb-present`），任一条不满足时 meson 只给
warning 而不中断 —— 结果：**rootfs 里 libEGL 有了，但没有 zink 驱动**，
EGL 只能落到 softpipe 软渲染，所有走 GL 的游戏 / D3D 老程序"慢得离谱"。

**修法**：把「请求」升级为「验收」——`install()` 阶段新增硬校验：

1. `libEGL.so` / `libGLESv2.so` / `libGL.so` 缺任一 → **构建失败**；
2. aarch64 形态下扫描 `libgallium_dri.so` / `libgallium*.so` / `libdri_*.so`，
   找不到 `zink` 驱动字符串 → **构建失败**（并打印 4 条前置条件复核清单）。

宁可在 CI 炸掉，也不要再让"没有 zink 的 rootfs"静默流出去。

### 2.2 mesa 构建档位

- 显式补 `-Dbuildtype=release -Doptimization=3`（rootfs 框架虽已注入
  `--buildtype=release`，但独立构建路径不经过框架；显式声明零风险）。

### 2.3 运行时（App 侧调用链）

- **性能档新增 `WINE_FULLSCREEN_FSR=1`**（wine 的 FSR 1.0 全屏升采样：
  GPU 负载按面积比下降，1080p→720p 约 -55%，观感损失有限）。
  仅在**性能档**默认开启（其余档位画面锐度优先），用户可用容器 `env=` /
  opt conf 逐项覆盖（`putIfAbsent`）。
- 已复核并沿用既有的 WinFusion / WinlatorXR 同源调优串（未重复造轮子）：
  `MESA_VK_WSI_PRESENT_MODE=mailbox` / `MESA_NO_ERROR=1` /
  `ZINK_DESCRIPTORS=lazy` / `DXVK_ASYNC=1` + `DXVK_STATE_CACHE_PATH` /
  `WINEDEBUG=-all` / box64 四档 dynarec 预设 JSON。

### 2.4 wine / box64 构建复核结论

- wine：`--disable-tests --without-unwind --with-vulkan --with-gstreamer`
  + 框架 `-O3 -flto=thin`；arm64ec 配方 `CROSSCFLAGS="-O3 -pipe"`、PE 侧
  经 llvm-mingw 交叉编译，**未动 LTO**（llvm-mingw + ThinLTO 的链接插件
  风险高，收益 ~5%，不做赌博性改动）。
- box64：`-DANDROID=ON -DBAD_SIGNAL=ON -DARM_DYNAREC=ON -DNOLOADADDR=ON`
  已含 dynarec（x86_64 吞吐主旋钮）+ 运行期 `BOX64_DYNAREC=1` /
  `BOX64_X11GLX=1` / `BOX64_MMAP32=1`（性能档）/ 四档 dynarec 参数表。

### 2.5 X11 显示更新

- 内置 termux-x11 的 4 个 ABI `libXlorie.so` 与上游 fork
  （jiaxinchen-max/termux-app `master-x11-submodule`）**md5 逐字节一致**
  —— 原生层已是该 fork 最新；Java 层 = fork 版 + AnWind 加固（prefs 未就位
  判空、分辨率容错解析等）。
- 上游 termux-x11 master 的 JNI ABI 已改为 ptr 形态（`nativeInit(long ptr)`、
  `sendKeyEvent(..., boolean)` 等），与本 fork 的 `.so` **不兼容**，无法
  直接换核（换核 = 崩溃）。故本次把上游**较新的触摸语义**移植进 App 侧
  Kotlin 桥（见第 3 节），这是当前 ABI 下唯一安全的"更新 X11"路径。
- 另修一处显示语义 bug：手动在控制条设分辨率时不再被标成"glibc-runner
  握手"（旧实现 `fromGame=true` → 弹出误导性 Toast + 状态条把手动设置
  标成游戏分辨率）。新增 `apply(value, fromGameSource)` 与
  `setExact/setNative` 的手动通道。

## 3. X11 三种触摸方式修 bug（用户问题 1 后半）

对照上游 termux-x11 `InputStrategyInterface`（`TrackpadInputStrategy` /
`SimulatedTouchInputStrategy` / `NullInputStrategy`）与
`TouchInputHandler.GestureListener` 逐条复核 App 侧 `SmartTouchBridge`，
修复 4 处真实缺陷：

| 触摸方式 | 缺陷 | 修复 |
|---|---|---|
| 触控板 | **轻点拖拽（tapToMove）拖拽结束后左键永久卡在按下** —— 抬起分支因 `moved=true` 被跳过，此后所有点击都变拖拽、窗口乱跑 | 拖拽结束统一释放左键（对齐上游 ACTION_UP → sendMouseUp 语义） |
| 触控板 / 模拟触摸 | **三指轻点被吞** —— 只区分 1/2 指，中键（自动瞄准 / 新标签页）无法触发 | 记录 `maxPointers`，三指轻点 = 中键（对齐上游 `mouseButtonFromPointerCount`） |
| 模拟触摸 / 触控板 | 双指阶段的右键落点用的是单指阶段的旧坐标 → 点空白处右键跑到别处 | 双指阶段同步 `curX/curY`，右键/中键落在手指当前位置 |
| 直接触摸 | **新手势把上一手势遗留的活跃触摸静默丢弃**（`Arrays.fill(-1)` 不发 TouchEnd）→ X 侧认为手指仍按着 → 触摸仿真按钮卡按 → 此后点击全失灵 | 清槽位前先给遗留槽位补发 `TouchEnd` |

另：`reloadTouchPrefs` 切方式时的状态归位已覆盖 tapToMove 按下态
（`resyncStuckPress` 同步释放）。

## 5. 虚拟手柄（用户问题 3）

### 5.1 悬浮球菜单被挡 / 位置不对 / 点击失效

**根因**：旧结构里 `GamepadFloatingBall`（含全屏捕获层 + 菜单 + 球）挂在
手柄覆盖层的**第一个**子位 → 捕获层/菜单/球全部压在摇杆与 ABXY 按钮
**之下**：菜单被按钮视觉覆盖（M 按钮正好压在「手柄设置」上）、按钮的
pointerInput 先命中把菜单点击全部吃掉、菜单还向右溢出屏幕右缘被裁掉。

**修复**（`GamepadOverlay.kt` / `GamepadFloatingBall.kt`）：

- **z 序重排为三层**：① 全屏捕获层（最底）→ ② 手柄元素（中）→
  ③ 菜单 + 悬浮球（最顶）；展开态提升到 `GamepadController.ballMenuExpanded`
  以便跨层共享。
- **菜单定位重写**：球右侧放不下时**翻到球的左侧**，否则以球心居中；
  球下方放不下时翻到球上方；两向都放不下时钳制进屏 —— 永不溢出；
  菜单高度用**实测值**（`onGloballyPositioned` 回填）而非估算。
- **菜单命中矩形生命周期**：收起 / 离场时 `clearMenuHit()` 置 null
  （旧式零尺寸矩形在 ±12px 外扩下仍会命中屏幕左上角，导致该处触摸被
  X11 触摸桥误剥离 → 点不动）。

### 5.2 配置文件功能（.vgp）

**新增** `core/input/gamepad/GamepadConfigFile.kt`：

- 后缀 **.vgp**（**V**irtual **G**ame **P**ad，三字母缩写）；
- 文件内容 = `GamepadController.toJson()` 原样 JSON（v3 布局：elements +
  padVisible + ballX/ballY），与 App 内 `gamepad_config` 同格式，存读互通；
- 保存走 SAF `CreateDocument`（建议名 `anwind_gamepad.vgp`），
  读取走 SAF `OpenDocument`；另提供 App 私有目录同名文件的
  `exportToPrivateFile` / `importFromPrivateFile`（终端 / 调试用）；
- 设置面板顶栏新增「💾 保存配置」「📂 读取配置」两个 chip，读入后立即
  持久化并释放所有按键。

### 5.3 配置界面上移

`GamepadSettingsWindow` 由**贴底居中**（bottom = 8dp）改为**顶部居中**
（top = 48dp）—— 旧位置正好压住经典布局的十字键（0.38/0.72）与「≡」
按钮（0.50/0.82），面板与手柄本体不再互相遮挡。

### 8.4 winegstreamer 修复的实证（对真实 proton_9.0 源码树）

不再只做「补丁能打上」这种弱验证，本轮做了三层实证：

1. **根因对照真实源码**：从 ValveSoftware/wine 取 `proton_9.0` 与 `proton_10.0` 的
   `dlls/winegstreamer/unixlib.c`（GitHub contents API，base64 原样）——
   proton_9.0 的架构判定确实只有 x86 两支且带 `#error Bad arch`；
   proton_10.0 已有 `__aarch64__` 分支。
2. **补丁实打**：上游补丁与本版兜底补丁对 proton_9.0 原文件均
   `patch -p1 --forward --fuzz=0` **干净应用**，两者 hunk 内容**逐字一致**
   （都是 Valve proton_10.0 的 `__aarch64__` → `/registry.aarch64.bin`）。
3. **预处理器实证**（用 host gcc 模拟三种目标架构）：

| 目标 | 补丁前 | 补丁后 |
|---|---|---|
| aarch64 | `#error Bad arch`（gcc 退出码 1）= CI 原始阵亡点 | `/registry.aarch64.bin`，退出码 0 ✅ |
| x86_64 | `/registry.x86_64.bin` | `/registry.x86_64.bin`（**行为逐位不变**）✅ |
| i386 | `/registry.i386.bin` | `/registry.i386.bin`（**行为逐位不变**）✅ |

> 第 3 行是关键：**该补丁对 x86_64 形态的 wine 构建没有任何影响**
> （unix 侧 = x86_64 → 首个分支即命中），所以 x86_64 那条线的红与它无关，
> 真正的原因是 libogg 下载 + mesa 的 buildtype 撞车（均已修）。
